# SmartCap Interface Specification v1

## 1. Purpose

This document defines the communication interface between:

- Team 1: IMU and Haptic
- Team 2: ESP32 Camera and Communication
- Team 3: AI and Computer Vision
- Edge Gateway: Laptop or Raspberry Pi

All teams must follow this document when exchanging data.

---

## 2. System Data Flow

```text
IMU + Camera
     ↓
ESP32 / Arduino during development
     ↓
Wi-Fi / USB Serial
     ↓
Laptop or Raspberry Pi
     ↓
AI and Sensor Fusion
     ↓
Driver State and Risk Score
     ↓
Vibration Command
```

---

## 3. Time Convention

During development, the Laptop is the main reference clock.

Every message should contain:

- `device_timestamp_ms`: timestamp generated by the device.
- `received_timestamp_ms`: timestamp generated when the Laptop receives the message.
- `sequence_id`: increasing message number.

The device clocks are not assumed to be synchronized.

### Example

```json
{
  "device_timestamp_ms": 123456,
  "received_timestamp_ms": 123789,
  "sequence_id": 842
}
```

### Rules

- All timestamps are in milliseconds.
- `sequence_id` starts from zero or one and increases by one.
- A missing sequence number indicates a possible lost packet.
- The Laptop must record packet loss and communication delay.

---

## 4. Units

All teams must use the following units:

| Signal | Unit |
|---|---|
| Accelerometer | g |
| Gyroscope | degrees per second |
| Pitch | degrees |
| Roll | degrees |
| Duration | milliseconds |
| Risk score | 0.0 to 1.0 |
| Quality score | 0.0 to 1.0 |
| FPS | frames per second |
| Latency | milliseconds |

### Important

The MPU6050 does not provide a reliable absolute yaw value because it has no magnetometer and gyroscope integration causes drift.

Raw gyroscope values can still be used:

```text
gx_dps
gy_dps
gz_dps
```

---

## 5. Common Status Values

All sensors and modules should use one of the following status values:

```text
OK
DEGRADED
INVALID
DISCONNECTED
CALIBRATING
UNKNOWN
```

### Meaning

- `OK`: data is valid and usable.
- `DEGRADED`: data is usable but quality is reduced.
- `INVALID`: data is not reliable.
- `DISCONNECTED`: device or sensor is not connected.
- `CALIBRATING`: calibration is currently running.
- `UNKNOWN`: the system cannot determine whether the data is valid.

---

## 6. Quality Score

Every data source should provide a quality score:

```text
0.0 = unusable
1.0 = high quality
```

Examples:

```json
{
  "imu_status": "OK",
  "imu_quality": 0.91
}
```

```json
{
  "camera_status": "DEGRADED",
  "camera_quality": 0.42
}
```

The AI system must not trust a low-quality source normally.

### Fusion Rules

```text
All sources valid:
    Use normal sensor fusion.

One source degraded:
    Use weighted fusion and reduce confidence.

No reliable source:
    Output UNKNOWN.

Sensor conflict:
    Reduce confidence and investigate the conflict.

Communication timeout:
    Output UNKNOWN and report a diagnostic warning.
```

# 7. IMU Message

Team 1 must produce IMU messages using the following structure.

```json
{
  "type": "imu",
  "device_id": "smartcap_01",
  "sequence_id": 842,
  "device_timestamp_ms": 123456,
  "received_timestamp_ms": 123789,

  "ax_g": 0.02,
  "ay_g": -0.11,
  "az_g": 0.98,

  "gx_dps": 1.2,
  "gy_dps": -4.8,
  "gz_dps": 0.6,

  "pitch_deg": 8.4,
  "roll_deg": -1.7,
  "pitch_velocity_dps": -12.1,

  "head_down_duration_ms": 420,
  "nodding_score": 0.31,
  "motion_energy": 0.18,

  "imu_status": "OK",
  "calibration_status": "CALIBRATED",
  "imu_quality": 0.91
}
```

## IMU Field Description

| Field | Description |
|---|---|
| `type` | Message type; must be `imu` |
| `device_id` | Device identifier |
| `sequence_id` | Increasing message number |
| `device_timestamp_ms` | Device timestamp |
| `received_timestamp_ms` | Laptop timestamp |
| `ax_g`, `ay_g`, `az_g` | Acceleration |
| `gx_dps`, `gy_dps`, `gz_dps` | Angular velocity |
| `pitch_deg` | Pitch angle |
| `roll_deg` | Roll angle |
| `pitch_velocity_dps` | Pitch angular velocity |
| `head_down_duration_ms` | Current head-down duration |
| `nodding_score` | Nodding confidence from 0 to 1 |
| `motion_energy` | Motion intensity |
| `imu_status` | IMU status |
| `calibration_status` | Calibration status |
| `imu_quality` | IMU quality from 0 to 1 |

## Initial IMU Labels

The initial dataset may use:

```text
normal
look_down
nod
rapid_turn
still
```

These labels are for development and do not directly mean clinical drowsiness.

# 8. Camera Frame Message

Team 2 must provide camera frames with the following metadata.

```json
{
  "type": "camera_frame",
  "device_id": "smartcap_01",
  "frame_id": 431,
  "device_timestamp_ms": 123480,
  "received_timestamp_ms": 123820,

  "width": 320,
  "height": 240,
  "jpeg_quality": 10,
  "actual_fps": 9.8,

  "camera_status": "OK",
  "camera_quality": 0.88
}
```

## Camera Field Description

| Field | Description |
|---|---|
| `type` | Message type; must be `camera_frame` |
| `device_id` | Camera device identifier |
| `frame_id` | Increasing frame number |
| `device_timestamp_ms` | Camera timestamp |
| `received_timestamp_ms` | Laptop timestamp |
| `width` | Frame width in pixels |
| `height` | Frame height in pixels |
| `jpeg_quality` | JPEG quality setting |
| `actual_fps` | Measured FPS |
| `camera_status` | Camera status |
| `camera_quality` | Camera quality from 0 to 1 |

The image data may be transmitted as JPEG or another agreed binary format. The metadata must remain consistent.

# 9. Vision Features

Team 3 should generate vision features in a separate internal structure.

```json
{
  "type": "vision_features",
  "frame_id": 431,
  "timestamp_ms": 123820,

  "face_detected": true,
  "face_confidence": 0.96,
  "eye_visibility": 0.91,

  "ear": 0.21,
  "mar": 0.48,
  "eye_closed": true,
  "eye_closure_duration_ms": 740,
  "blink_score": 0.72,
  "yawn_score": 0.31,

  "face_orientation_pitch_deg": 5.2,
  "face_orientation_roll_deg": -1.4,

  "vision_status": "OK",
  "vision_quality": 0.89
}
```

### Important

The field:

```text
face_orientation
```

means face orientation relative to the wearable camera.

It does not automatically mean:

```text
driver looking away from the road
```

Road-relative gaze estimation is outside the Core scope unless a fixed cabin camera is added.

# 10. Driver State Message

Team 3 must produce the final driver-state output using the following structure.

```json
{
  "type": "driver_state",
  "timestamp_ms": 124200,

  "state": "DROWSINESS_SUSPECTED",
  "risk_level": "HIGH",
  "risk_score": 0.84,
  "confidence": 0.88,

  "camera_quality": 0.92,
  "imu_quality": 0.81,

  "evidence": [
    "long_eye_closure",
    "repeated_nodding"
  ],

  "system_status": "OK"
}
```

## Allowed Driver States

```text
ATTENTIVE
DISTRACTED
DROWSINESS_SUSPECTED
HIGH_RISK
UNKNOWN
```

## Allowed Risk Levels

```text
LOW
MEDIUM
HIGH
CRITICAL
UNKNOWN
```

## Important

`UNKNOWN` must be used when:

- Face is not detected.
- Eyes are not visible.
- Camera quality is too low.
- IMU is disconnected.
- IMU is not calibrated.
- Data is too old.
- Packet loss is too high.
- Camera and IMU signals conflict strongly.

The system must not convert missing data into `ATTENTIVE`.

# 11. Vibration Command

The AI or Edge Gateway sends commands to Team 1.

```json
{
  "type": "vibration_command",
  "command_id": 77,
  "timestamp_ms": 124220,

  "level": 2,
  "duration_ms": 500,
  "reason": "HIGH_RISK_DROWSINESS"
}
```

## Vibration Levels

```text
0 = STOP
1 = WARNING
2 = HIGH_RISK
3 = CRITICAL
```

## Allowed Reasons

```text
HIGH_RISK_DROWSINESS
PROLONGED_EYE_CLOSURE
REPEATED_NODDING
COMMUNICATION_FAILURE
SENSOR_FAILURE
MANUAL_TEST
```

Team 1 must stop vibration automatically after the requested duration unless a repeated command is received.

---

# 12. Communication Timeout

The system must detect communication failures.

Initial development values:

```text
IMU timeout:
    configurable

Camera timeout:
    configurable

Gateway timeout:
    configurable
```

The exact timeout values must be measured experimentally.

When a timeout occurs:

```text
Data source status = DISCONNECTED
Driver state = UNKNOWN
Diagnostic warning = ON
```

# 13. Dataset Rules

## Public Datasets

Public datasets such as NTHU-DDD and YawDD are used for:

```text
Vision baseline
Feature testing
Initial model development
```

They are not considered synchronized camera-plus-IMU datasets.

## Private Synchronized Dataset

The team must collect its own synchronized data containing:

```text
Camera frames
IMU readings
Timestamps
Participant code
Activity label
Lighting condition
Hardware version
```

## Data Split

The same participant must not appear in both training and final testing.

Use:

```text
Training participants
Validation participants
Test participants
```

Do not split random frames from the same video into training and test.

---

# 14. Privacy and Ethics

- Obtain written consent from every participant.
- Do not intentionally deprive anyone of sleep.
- Drowsiness-related behavior should be simulated.
- Test in a parked vehicle or simulator only.
- Do not test drowsiness while driving on public roads.
- Do not upload participant videos to GitHub.
- Use participant codes instead of names.
- Raw video should not be stored in the final system.
- Local processing is preferred.
- The system is not a medical diagnostic tool.
- The system is not a certified automotive safety system.
- The CAN prototype must not control brakes, throttle, or steering.
